# Task Sync Backend API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Django `tasks` app exposing a per-user CRUD API for tasks (list/create/retrieve/update/delete), mirroring the frontend `Task` shape, so a later frontend change can make it the real source of truth instead of localStorage.

**Architecture:** One `Task` model in a new `backend/apps/tasks/` app, following `backend/apps/accounts/`'s existing style exactly (plain DRF `generics` views, explicit `path()` entries added to the shared `config/urls.py`, no viewsets/routers). Every field maps 1:1 to `frontend/src/features/tasks/types.ts`'s `Task` interface. The server is a dumb per-user CRUD store — no business logic (rollover, routine materialization) moves server-side; that stays exactly where it already lives, client-side.

**Tech Stack:** Django 5, Django REST Framework, Simple JWT (already installed and configured — no new dependencies). All commands below run from `backend/`, using the project's existing venv: `.venv/Scripts/python.exe` (Windows) — substitute `.venv/bin/python` if run on macOS/Linux.

## Global Constraints

- Mirror `apps/accounts`'s file layout and style exactly: `models.py`, `serializers.py`, `views.py`, `tests.py`, `apps.py`; plain `generics`/`APIView` classes; `IsAuthenticated` set explicitly per view even though it's already the project default (matches `MeView`'s existing style); explicit `path()` entries added directly to `config/urls.py` (no app-level `urls.py` include, no viewsets/routers).
- The server does not implement or duplicate any scheduling logic (rollover, routine materialization) — it only stores and returns whatever task rows the client sends. No task in this plan touches `frontend/`.
- **`backend/.env` has real Oracle credentials configured** (`ORACLE_DB_USER`, `ORACLE_DB_PASSWORD`, `ORACLE_DB_DSN` are all set), so `config/settings.py`'s `DATABASES` conditional will pick Oracle, not the sqlite fallback, for any plain `manage.py` invocation. Every command in this plan that touches a database connection (`migrate`, `test`) must override those three variables to empty first, forcing the sqlite fallback:
  ```
  ORACLE_DB_DSN= ORACLE_DB_USER= ORACLE_DB_PASSWORD= .venv/Scripts/python.exe manage.py <command>
  ```
  (`django-environ`'s `read_env()` only fills in a variable that isn't already present in the process environment — see the comment already in `config/settings.py` above `environ.Env.read_env(...)` — so explicitly setting these to empty strings, not merely leaving them unset, is what actually prevents the `.env` file's values from taking effect.) This plan intentionally never runs a migration against the real Oracle instance — that's a live shared resource and is left for the human to do themselves when ready to actually use it in production.
- Every new field/behavior in this plan must have a covering test — this is a synced, per-user data store; an untested gap here is a real cross-user data leak risk, not just a missed feature.

- [ ] **Step 2: Write the model**

  Create `backend/apps/tasks/models.py`:

  ```python
  from django.conf import settings
  from django.db import models


  SCOPE_KIND_CHOICES = [
      ("day", "day"),
      ("week", "week"),
      ("month", "month"),
      ("year", "year"),
  ]


  class Task(models.Model):
      id = models.UUIDField(primary_key=True, editable=True)
      user = models.ForeignKey(
          settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name="tasks"
      )
      title = models.CharField(max_length=500)
      memo = models.TextField(blank=True, null=True)
      done = models.BooleanField(default=False)
      scope_kind = models.CharField(max_length=10, choices=SCOPE_KIND_CHOICES)
      scope_value = models.CharField(max_length=20)
      rolled_from_kind = models.CharField(
          max_length=10, blank=True, null=True, choices=SCOPE_KIND_CHOICES
      )
      rolled_from_value = models.CharField(max_length=20, blank=True, null=True)
      created_at = models.CharField(max_length=32)
      completed_at = models.CharField(max_length=32, blank=True, null=True)
      time = models.CharField(max_length=5, blank=True, null=True)
      subtasks = models.JSONField(default=list, blank=True)
      repeat_weekdays = models.JSONField(blank=True, null=True)
      repeat_source = models.ForeignKey(
          "self",
          null=True,
          blank=True,
          on_delete=models.SET_NULL,
          related_name="occurrences",
      )
      excluded_dates = models.JSONField(blank=True, null=True)
      priority = models.BooleanField(blank=True, null=True)
      duration_minutes = models.PositiveIntegerField(blank=True, null=True)
      background = models.BooleanField(blank=True, null=True)
      updated_at = models.DateTimeField(auto_now=True)

      class Meta:
          indexes = [models.Index(fields=["user"])]

      def __str__(self):
          return self.title
  ```

  `id` needs `editable=True`: DRF's `ModelSerializer` auto-generates a
  `read_only` serializer field for any model field where `editable=False`
  (Django's default for primary keys) — without this, the client-sent
  `id` would silently be dropped on create.

  `repeat_source` (not `repeat_source_id`) — Django auto-appends `_id` to
  a FK field's own name for its DB column and gives you
  `instance.repeat_source_id` as the raw-value accessor for free either
  way, so naming the field itself with a trailing `_id` would double up
  into a `repeat_source_id_id` column.

              "/api/tasks/",

- [ ] **Step 7: Write the serializer**

  Create `backend/apps/tasks/serializers.py`:

  ```python
  from rest_framework import serializers

  from .models import Task


  class TaskSerializer(serializers.ModelSerializer):
      id = serializers.UUIDField()
      repeat_source = serializers.PrimaryKeyRelatedField(
          queryset=Task.objects.none(), allow_null=True, required=False
      )

      class Meta:
          model = Task
          fields = (
              "id",
              "title",
              "memo",
              "done",
              "scope_kind",
              "scope_value",
              "rolled_from_kind",
              "rolled_from_value",
              "created_at",
              "completed_at",
              "time",
              "subtasks",
              "repeat_weekdays",
              "repeat_source",
              "excluded_dates",
              "priority",
              "duration_minutes",
              "background",
          )

      def __init__(self, *args, **kwargs):
          super().__init__(*args, **kwargs)
          request = self.context.get("request")
          if request is not None and request.user.is_authenticated:
              self.fields["repeat_source"].queryset = Task.objects.filter(user=request.user)
  ```

  The `repeat_source` queryset starts as `Task.objects.none()` and is
  narrowed to the requesting user's own tasks in `__init__` — this is
  what makes "points at another user's task" a validation error (DRF's
  `PrimaryKeyRelatedField` rejects any value outside its queryset) rather
  than a security hole.

- [ ] **Step 8: Write the views**

  ```python
  from rest_framework import generics, permissions

  from .models import Task
  from .serializers import TaskSerializer


  class TaskListCreateView(generics.ListCreateAPIView):
      serializer_class = TaskSerializer
      permission_classes = (permissions.IsAuthenticated,)

      def get_queryset(self):
          return Task.objects.filter(user=self.request.user)

      def perform_create(self, serializer):
          serializer.save(user=self.request.user)


  class TaskDetailView(generics.RetrieveUpdateDestroyAPIView):
      serializer_class = TaskSerializer
      permission_classes = (permissions.IsAuthenticated,)

      def get_queryset(self):
          return Task.objects.filter(user=self.request.user)
  ```

  No `lookup_field` override needed — the model's primary key is already
  named `id`, and DRF's default lookup (`pk`, matched against a URL kwarg
  named `pk`) resolves to it automatically.
