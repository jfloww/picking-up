# Deployment Runbook

Step-by-step commands to get the backend live on the existing OCI VM and
the frontend live on Vercel. Design rationale for these choices lives in
`docs/superpowers/specs/2026-08-05-production-deployment-design.md` — this
doc is the "how," that one is the "why."

Run this after `docs/superpowers/plans/2026-08-05-production-deployment-code-changes.md`
has landed (whitenoise/gunicorn added, settings updated) — steps below
assume that's already merged.

## 0. Verify VM access

(The `key/` paths referenced here and in Step 4 — the SSH key,
`key/db-settings.txt` — live on your local machine, not the VM. `key/` is
gitignored, so a `git clone` on the VM itself won't have them.)

```
ssh -i "key/ssh-key-2026-07-14.key" opc@129.213.191.36
```

If this hangs or refuses: check the OCI console — the instance's public IP
is ephemeral by default and can change across a stop/start. If it changed,
update every place `129.213.191.36` is used below (this doc, `key/db-settings.txt`,
and any DNS record from Step 2) with the new IP.

Once connected, confirm the VM's actual state before touching anything —
per the design spec this "could not be verified from this session," so
don't assume:
```
cat /etc/os-release        # confirm Oracle Linux 8 vs 9 — determines the EPEL release package in Step 1
dnf list --available python3.11
sudo systemctl status nginx gunicorn 2>&1 | head -20   # confirm nothing is already running (state genuinely unknown per the design spec)
```

## 1. Install OS packages on the VM

```
sudo dnf install -y oracle-epel-release-el9   # use oracle-epel-release-el8 if Step 0's os-release check showed OL8
sudo dnf install -y python3.11 python3.11-pip nginx certbot python3-certbot-nginx git firewalld
sudo systemctl enable --now firewalld
```

## 2. DuckDNS hostname

1. Sign up at duckdns.org (free), create a subdomain, e.g. `pickingup`.
2. Point it at `129.213.191.36` from the DuckDNS dashboard.
3. Confirm it resolves: `nslookup pickingup.duckdns.org` (from any machine)
   should return `129.213.191.36`.
4. Optional but recommended — a cron job on the VM that re-pushes the
   current IP on a schedule, as a safety net if the instance's IP ever
   changes without you noticing:
   ```
   */30 * * * * curl -s "https://www.duckdns.org/update?domains=pickingup&token=<your-duckdns-token>&ip=" >/dev/null 2>&1
   ```
   Add via `crontab -e` on the VM. Keep the token out of this repo.

## 3. Clone and set up the app on the VM

```
git clone <this repo's URL> ~/picking-up
cd ~/picking-up/backend
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

## 4. Production `.env` on the VM

Create `~/picking-up/backend/.env` (never committed — this file only ever
exists on the VM and in your local dev checkout):

```
DJANGO_SECRET_KEY=<generate with the command below>
DJANGO_DEBUG=False
DJANGO_ALLOWED_HOSTS=pickingup.duckdns.org
DJANGO_CORS_ALLOWED_ORIGINS=https://<your-vercel-domain>.vercel.app
DJANGO_CSRF_TRUSTED_ORIGINS=https://pickingup.duckdns.org
DJANGO_NUM_PROXIES=1
DJANGO_CACHE_LOCATION=/home/opc/picking-up/backend/.cache

GOOGLE_OAUTH_CLIENT_ID=<same client ID as the frontend's NEXT_PUBLIC_GOOGLE_CLIENT_ID>

ORACLE_DB_USER=<from your July OCI setup>
ORACLE_DB_PASSWORD=<from your July OCI setup>
ORACLE_DB_DSN=<the descriptor already in key/db-settings.txt>
```

`DJANGO_NUM_PROXIES=1` matches the single nginx hop in this runbook. It makes
DRF authentication throttles use the client address nginx appends to
`X-Forwarded-For`, rather than treating every request as `127.0.0.1`. Do not
increase it unless another trusted reverse proxy is actually added. Django
creates `DJANGO_CACHE_LOCATION` with owner-only permissions; all gunicorn
workers on this VM use that directory for shared throttle state.

Lock down the file's permissions immediately — it holds the Django secret
key and the Oracle DB password, and the default umask would otherwise leave
it world-readable:
```
chmod 600 ~/picking-up/backend/.env
```

Generate the secret key:
```
.venv/bin/python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```
If the generated value contains characters like `#`, `$`, `&`, `(`, `)`,
single-quote it in `.env` (e.g. `DJANGO_SECRET_KEY='abc#def$ghi'`) — see the
caution in Step 6 about `EnvironmentFile=` and shell-like unquoting.

`DJANGO_CORS_ALLOWED_ORIGINS` can't be filled in for real until Step 8
(Vercel) gives you the actual domain — come back and update it then.

## 5. First-run Django tasks

```
cd ~/picking-up/backend
.venv/bin/python manage.py migrate
.venv/bin/python manage.py collectstatic --noinput
```

`migrate` is idempotent — safe to re-run even though the DB was already
migrated once in July.

## 6. gunicorn as a systemd service

Create `/etc/systemd/system/gunicorn.service`:

```ini
[Unit]
Description=gunicorn for picking-up backend
After=network.target

[Service]
User=opc
WorkingDirectory=/home/opc/picking-up/backend
EnvironmentFile=/home/opc/picking-up/backend/.env
ExecStart=/home/opc/picking-up/backend/.venv/bin/gunicorn config.wsgi:application --bind 127.0.0.1:8000 --workers 2
Restart=always

[Install]
WantedBy=multi-user.target
```

Caution: `EnvironmentFile=` does its own shell-like unquoting (different
from how `django-environ` reads `.env`). If `DJANGO_SECRET_KEY` or any other
value in `.env` contains characters like `#`, `$`, `&`, `(`, `)` — which
`get_random_secret_key()` can produce — wrap the value in single quotes
(e.g. `DJANGO_SECRET_KEY='abc#def$ghi'`), or the unit can fail to start with
a confusing error visible only in `journalctl`, not in Django.

```
sudo systemctl daemon-reload
sudo systemctl enable --now gunicorn
sudo systemctl status gunicorn   # confirm "active (running)"
```

Sanity check from the VM itself:
```
curl -H "Host: pickingup.duckdns.org" -i http://127.0.0.1:8000/api/tasks/
```
Expect `401 Unauthorized` (not a connection error) — that's success, it
proves Django/DRF is handling the request correctly. A bare `curl
http://127.0.0.1:8000/...` without the `Host` header gets rejected with
Django's 400 DisallowedHost instead, since `DJANGO_ALLOWED_HOSTS` doesn't
include `127.0.0.1` in production — that's not a sign anything's broken.

## 7. nginx + HTTPS

### 7a. nginx config + VM-level firewall + SELinux

Create `/etc/nginx/conf.d/pickingup.conf`:

```nginx
server {
    listen 80;
    server_name pickingup.duckdns.org;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

```
sudo systemctl enable --now nginx
sudo nginx -t && sudo systemctl reload nginx

# Firewall — VM-level (firewalld). Cloud-level is 7b below — do it before
# running certbot in 7c, don't skip it.
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload

# SELinux is enforcing by default on Oracle Linux and otherwise blocks
# nginx's proxy_pass to gunicorn on 127.0.0.1:8000 — every request 502s,
# and the only trace of why is an SELinux denial in
# /var/log/audit/audit.log, not in the nginx or gunicorn logs. See Step 11
# if you hit a 502 after the fact.
sudo setsebool -P httpd_can_network_connect 1
```

### 7b. Firewall — cloud level (the step that's easy to forget)

In the OCI console: **Networking → Virtual Cloud Networks → (your VCN) →
Security Lists** (or the VM's attached Network Security Group, whichever
this instance uses) → add ingress rules:
- `443/tcp` from `0.0.0.0/0`
- `80/tcp` from `0.0.0.0/0` (needed for the certbot HTTP-01 challenge and
  the HTTP→HTTPS redirect)

`curl` working from the VM itself but failing from anywhere else almost
always means this step, not 7a's firewalld rules, was missed.

Do this **before** 7c — certbot's HTTP-01 challenge needs Let's Encrypt to
reach port 80 from the public internet, which is exactly what this step
enables. Running certbot before this step is done fails with a connection
timeout.

### 7c. certbot

```
# Certbot obtains the cert and rewrites the nginx config above to add the
# HTTPS server block + HTTP->HTTPS redirect automatically.
sudo certbot --nginx -d pickingup.duckdns.org

# Certs are 90-day. EPEL's certbot package ships a renewal timer but
# doesn't enable it by default — turn it on and verify it actually works
# now, not in 90 days when it silently didn't.
sudo systemctl enable --now certbot-renew.timer
sudo certbot renew --dry-run     # also re-validates that port 80 stayed reachable
```

## 8. Frontend on Vercel

1. vercel.com → New Project → import this GitHub repo.
2. Set the project's root directory to `frontend/`.
3. Environment variables (Vercel project settings → Environment Variables):
   ```
   DJANGO_API_BASE_URL=https://pickingup.duckdns.org
   NEXT_PUBLIC_GOOGLE_CLIENT_ID=<existing Google OAuth client ID>
   NEXT_PUBLIC_APP_NAME=Picking Up
   ```
4. Deploy. Vercel gives you a `*.vercel.app` production URL — note it,
   you need it for Steps 9 and 10.

## 9. Backend CORS (optional defense-in-depth, not required for the app to work)

The browser never calls Django directly in this app's architecture —
Next.js's server-side code on Vercel (the BFF) is the only thing that calls
Django; `DJANGO_API_BASE_URL` is only ever read server-side. So this
setting has no effect on whether registration/login/tasks actually work —
it's harmless defense-in-depth at most. Still worth keeping in sync with
the real Vercel origin as hygiene, but don't go looking here first if
something else is broken.

Back on the VM, edit `~/picking-up/backend/.env`:
```
DJANGO_CORS_ALLOWED_ORIGINS=https://<the-real-vercel-domain>.vercel.app
```
```
sudo systemctl restart gunicorn
```

## 10. Google OAuth origin

Google Cloud Console → your OAuth 2.0 Client ID → **Authorized JavaScript
origins** → add `https://<the-real-vercel-domain>.vercel.app` (today only
local dev origins are authorized).

## 11. Smoke test

- `curl -i https://pickingup.duckdns.org/api/tasks/` from your own machine
  (not the VM) — should show a valid TLS handshake and a `401 Unauthorized`
  response. That's success (unauthenticated is expected — it proves
  nginx/gunicorn/Django are wired correctly end to end), not a connection
  error.
- Open the Vercel production URL in a browser. Register an account, log
  in, create a task, reload the page — confirms the full chain (Vercel →
  Django → Oracle DB) actually round-trips real data, not just that each
  piece boots.
- Also click "Sign in with Google" and confirm it works, not just the
  email path above — a missing `GOOGLE_OAUTH_CLIENT_ID` on the backend
  ships silently otherwise (Google sign-in just returns a 503, the email
  path is unaffected).
- If something's wrong: `journalctl -u gunicorn -n 50` and
  `~/picking-up/backend/logs/backend.log`/`backend-error.log` on the VM
  are the two places to look first. If you get a 502 and gunicorn's own
  logs look clean, it's likely an SELinux denial, not gunicorn or nginx —
  check `sudo ausearch -m avc -ts recent` or `/var/log/audit/audit.log`
  (see Step 7a).

## Future updates (after this first deploy)

Use a maintenance window for any release that includes migrations or changes
the task/category write contract. Old gunicorn workers must not keep writing
between a data backfill and its finalize migration.

```
ssh -i "key/ssh-key-2026-07-14.key" opc@129.213.191.36
sudo systemctl stop gunicorn
cd ~/picking-up && git pull
backend/.venv/bin/pip install -r backend/requirements.txt
backend/.venv/bin/python backend/manage.py migrate
backend/.venv/bin/python backend/manage.py collectstatic --noinput
sudo systemctl start gunicorn
```

If migration or smoke testing fails, keep gunicorn stopped until the database
and application versions are known to be compatible. Do not restart the old
application against a partially advanced schema.

Frontend updates are automatic — Vercel redeploys on every push to the
connected branch. For a cross-boundary API change, pause automatic production
promotion or use a backward-compatible expand/contract release so the backend
is ready before the new frontend becomes active. A migration plus an automatic
frontend deploy is not, by itself, an ordered cutover.
