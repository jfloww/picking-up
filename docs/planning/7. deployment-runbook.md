# Deployment Runbook

Step-by-step commands to get the backend live on the existing OCI VM and
the frontend live on Vercel. Design rationale for these choices lives in
`docs/superpowers/specs/2026-08-05-production-deployment-design.md` — this
doc is the "how," that one is the "why."

Run this after `docs/superpowers/plans/2026-08-05-production-deployment-code-changes.md`
has landed (whitenoise/gunicorn added, settings updated) — steps below
assume that's already merged.

## 0. Verify VM access

```
ssh -i "key/ssh-key-2026-07-14.key" opc@129.213.191.36
```

If this hangs or refuses: check the OCI console — the instance's public IP
is ephemeral by default and can change across a stop/start. If it changed,
update every place `129.213.191.36` is used below (this doc, `key/db-settings.txt`,
and any DNS record from Step 2) with the new IP.

## 1. Install OS packages on the VM

```
sudo dnf install -y python3.11 python3.11-venv nginx certbot python3-certbot-nginx git firewalld
sudo systemctl enable --now firewalld
```

## 2. DuckDNS hostname

1. Sign up at duckdns.org (free), create a subdomain, e.g. `pickingup`.
2. Point it at `129.213.191.36` from the DuckDNS dashboard.
3. Confirm it resolves: `nslookup pickingup.duckdns.org` (from any machine)
   should return `129.213.191.36`.
4. Optional but recommended — a cron job on the VM that re-pushes the
   current IP on a schedule, as a safety net if the instance's IP ever
   changes without you noticing:
   ```
   */30 * * * * curl -s "https://www.duckdns.org/update?domains=pickingup&token=<your-duckdns-token>&ip=" >/dev/null 2>&1
   ```
   Add via `crontab -e` on the VM. Keep the token out of this repo.

## 3. Clone and set up the app on the VM

```
git clone <this repo's URL> ~/picking-up
cd ~/picking-up/backend
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

## 4. Production `.env` on the VM

Create `~/picking-up/backend/.env` (never committed — this file only ever
exists on the VM and in your local dev checkout):

```
DJANGO_SECRET_KEY=<generate with the command below>
DJANGO_DEBUG=False
DJANGO_ALLOWED_HOSTS=pickingup.duckdns.org
DJANGO_CORS_ALLOWED_ORIGINS=https://<your-vercel-domain>.vercel.app

ORACLE_DB_USER=<from your July OCI setup>
ORACLE_DB_PASSWORD=<from your July OCI setup>
ORACLE_DB_DSN=<the descriptor already in key/db-settings.txt>
```

Generate the secret key:
```
.venv/bin/python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

`DJANGO_CORS_ALLOWED_ORIGINS` can't be filled in for real until Step 8
(Vercel) gives you the actual domain — come back and update it then.

## 5. First-run Django tasks

```
cd ~/picking-up/backend
.venv/bin/python manage.py migrate
.venv/bin/python manage.py collectstatic --noinput
```

`migrate` is idempotent — safe to re-run even though the DB was already
migrated once in July.

## 6. gunicorn as a systemd service

Create `/etc/systemd/system/gunicorn.service`:

```ini
[Unit]
Description=gunicorn for picking-up backend
After=network.target

[Service]
User=opc
WorkingDirectory=/home/opc/picking-up/backend
EnvironmentFile=/home/opc/picking-up/backend/.env
ExecStart=/home/opc/picking-up/backend/.venv/bin/gunicorn config.wsgi:application --bind 127.0.0.1:8000 --workers 2
Restart=always

[Install]
WantedBy=multi-user.target
```

```
sudo systemctl daemon-reload
sudo systemctl enable --now gunicorn
sudo systemctl status gunicorn   # confirm "active (running)"
```

Sanity check from the VM itself: `curl http://127.0.0.1:8000/api/` should
respond (not "connection refused").

## 7. nginx + HTTPS

Create `/etc/nginx/conf.d/pickingup.conf`:

```nginx
server {
    listen 80;
    server_name pickingup.duckdns.org;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

```
sudo systemctl enable --now nginx
sudo nginx -t && sudo systemctl reload nginx

# Firewall — VM-level (firewalld). Cloud-level is Step 7b, don't skip it.
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload

# Certbot obtains the cert and rewrites the nginx config above to add the
# HTTPS server block + HTTP->HTTPS redirect automatically.
sudo certbot --nginx -d pickingup.duckdns.org
```

### 7b. Firewall — cloud level (the step that's easy to forget)

In the OCI console: **Networking → Virtual Cloud Networks → (your VCN) →
Security Lists** (or the VM's attached Network Security Group, whichever
this instance uses) → add ingress rules:
- `443/tcp` from `0.0.0.0/0`
- `80/tcp` from `0.0.0.0/0` (needed for the certbot HTTP-01 challenge and
  the HTTP→HTTPS redirect)

`curl` working from the VM itself but failing from anywhere else almost
always means this step, not Step 7's firewalld rules, was missed.

## 8. Frontend on Vercel

1. vercel.com → New Project → import this GitHub repo.
2. Set the project's root directory to `frontend/`.
3. Environment variables (Vercel project settings → Environment Variables):
   ```
   DJANGO_API_BASE_URL=https://pickingup.duckdns.org
   NEXT_PUBLIC_GOOGLE_CLIENT_ID=<existing Google OAuth client ID>
   NEXT_PUBLIC_APP_NAME=Picking Up
   ```
4. Deploy. Vercel gives you a `*.vercel.app` production URL — note it,
   you need it for Steps 9 and 10.

## 9. Close the loop: backend CORS

Back on the VM, edit `~/picking-up/backend/.env`:
```
DJANGO_CORS_ALLOWED_ORIGINS=https://<the-real-vercel-domain>.vercel.app
```
```
sudo systemctl restart gunicorn
```

## 10. Google OAuth origin

Google Cloud Console → your OAuth 2.0 Client ID → **Authorized JavaScript
origins** → add `https://<the-real-vercel-domain>.vercel.app` (today only
local dev origins are authorized).

## 11. Smoke test

- `curl -I https://pickingup.duckdns.org/api/` from your own machine (not
  the VM) — should show a valid TLS handshake and an HTTP response.
- Open the Vercel production URL in a browser. Register an account, log
  in, create a task, reload the page — confirms the full chain (Vercel →
  Django → Oracle DB) actually round-trips real data, not just that each
  piece boots.
- If something's wrong: `journalctl -u gunicorn -n 50` and
  `~/picking-up/backend/logs/backend.log`/`backend-error.log` on the VM
  are the two places to look first.

## Future updates (after this first deploy)

```
ssh -i "key/ssh-key-2026-07-14.key" opc@129.213.191.36
cd ~/picking-up && git pull
backend/.venv/bin/pip install -r backend/requirements.txt
backend/.venv/bin/python backend/manage.py migrate
backend/.venv/bin/python backend/manage.py collectstatic --noinput
sudo systemctl restart gunicorn
```

Frontend updates are automatic — Vercel redeploys on every push to the
connected branch.
