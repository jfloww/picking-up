# Picking Up Mobile Web UX Preparation

Status: design preparation only. This document defines the mobile structure and behavior; it does not authorize or include frontend implementation.

## 1. Goal

Make the existing planner usable from 320px-wide mobile browsers without shrinking the desktop interface or removing task capabilities.

The mobile experience should optimize for three frequent jobs:

1. See what needs attention today.
2. Complete or add a task with one hand.
3. Open a task and change its schedule or details without depending on drag-and-drop.

The current desktop experience remains the reference for data, terminology, and visual character. Mobile changes information hierarchy and navigation, not the product identity.

## 2. Recommended decisions

| Area | Mobile decision | Reason |
| --- | --- | --- |
| Primary navigation | Persistent bottom navigation: Daily, Weekly, Monthly | Keeps all three destinations reachable without crowding the date header. |
| Daily landing | Open in `Tasks` mode | The task list is more scannable and actionable than a compressed 24-hour rail. |
| Daily split | Local `Tasks / Timeline` segmented switch | Replaces the desktop 60/40 panes while preserving both tools. |
| Date navigation | Sticky previous, date, Today, and next controls | Preserves explicit navigation; horizontal swipe is only an enhancement. |
| Task creation | Persistent `+ New task` dock above bottom navigation | Matches the desktop rule that quick add remains visible while tasks scroll. |
| Task details | Full-height sheet/page | The current side drawer is effectively screen-wide on phones and needs mobile-safe headers, fields, and actions. |
| Weekly view | Vertical seven-day agenda | Seven simultaneous columns are too narrow for touch and readable task titles. |
| Monthly view | Week-grouped list of day rows | Extends the mobile rendering pattern already present in `MonthGrid`. |
| Account/theme links | Compact overflow/profile menu | Removes the signed-in name and logout button from the narrow app bar. |
| Marketing footer | Omitted inside the mobile planner | Prevents product navigation and task space from competing with site-level links. |
| Drag-and-drop | Progressive enhancement only | Every operation must also be available through explicit controls. |

## 3. Responsive layout settings

### Breakpoint behavior

| Viewport | Planner structure |
| --- | --- |
| 320–479px | Compact mobile shell, 16px gutters, bottom navigation, single-pane content. |
| 480–639px | Same mobile shell with slightly wider task metadata and sheet spacing. |
| 640–1023px | Single-pane planner remains; navigation may move to a compact top tab row when space permits. |
| 1024px and wider | Preserve the existing desktop layout, including the Daily 60/40 split. |

Do not switch to the desktop Daily split merely because a phone is in landscape. A coarse-pointer device with limited height should continue using the single-pane model.

### Core measurements

| Element | Target |
| --- | --- |
| Mobile reference viewport | 390px wide |
| Minimum supported width | 320px |
| Horizontal gutter | 16px |
| Compact app bar | 52px plus top safe area |
| Date navigation block | 64–72px |
| Local segmented control | 40px |
| Bottom navigation | 60px plus bottom safe area |
| Quick-add dock | 52–56px |
| Standard touch target | At least 44 × 44px |
| Task row | Minimum 56px; 64px when secondary metadata is visible |
| Task-detail header | 56px plus top safe area |
| Task-detail action bar | 64px plus bottom safe area |
| Compact card radius | 10–12px |

Use the visual viewport when the software keyboard is open. The composer or detail action bar should stay above the keyboard, and the bottom navigation may temporarily hide to avoid stacking controls.

### App bar

- Keep the `PICKING UP` wordmark.
- Replace the visible user name and logout action with a 44px profile/overflow control.
- The overflow menu contains theme, account identity, sign out, home, and secondary site links.
- Do not put `New task` in this bar.

### Date block

- Show the active date as the strongest title.
- Retain the week-range subtitle in Daily view.
- Keep previous, Today, and next as explicit buttons.
- Preserve the same anchor date when switching between Tasks and Timeline.
- Optional horizontal swiping may change the active day, but all swipe behavior must have button and keyboard equivalents.

### Bottom navigation

- Destinations are exactly Daily, Weekly, and Monthly while Bucket List remains disabled.
- Each destination uses a Lucide icon and a visible text label.
- The selected item uses the brand color and a restrained active surface; inactive items use muted text.
- Respect `env(safe-area-inset-bottom)` for standalone and browser-installed experiences.
- Hide the bar while a full-height task or day-detail layer is active.

## 5. Screen blueprints

### 5.1 Daily — Tasks mode

This is the default mobile planner screen.

```text
All Day To-Do                              1
┌──────────────────────────────────────────┐
│ □  Grocery pickup              Priority │
│    All Day                               │
└──────────────────────────────────────────┘

Next Up
┌──────────────────────────────────────────┐
│ □  Finalize API proposal                 │
│    Overdue · 9:00–9:45 AM        2/3    │
└──────────────────────────────────────────┘
┌──────────────────────────────────────────┐
│ □  Prepare HMMA meeting notes            │
│    2:15 PM · 60m              Repeats   │
└──────────────────────────────────────────┘

Done Today                                 2
  ☑ Review pull request
  ☑ Gym
```

- Preserve the section names `All Day To-Do`, `Next Up`, and `Done Today`.
- Keep the checkbox independently tappable; tapping the rest of the row opens details.
- Show only the metadata needed to distinguish urgency or scheduling: time, overdue state, priority, repeat, due date, and subtask progress.
- Make `Done Today` collapsible after the first completed item when the list is long.
- Keep reorder handles visible only when reorder mode is entered or a long press begins. Hover-only affordances are not allowed.
- Use subtle entry/section-change motion and honor reduced-motion preferences.

### 5.2 Daily — Timeline mode

- Keep a vertical 24-hour rail with a 48–52px time gutter.
- Center the initial scroll around the current time for today and around 07:00 for other days, matching current behavior.
- Use full-width timed task cards in the remaining space.
- When background tasks exist, show them as a narrow muted lane or low-emphasis layer without making regular task titles unreadable.
- Show the current-time line and overdue, pending, completed, and background states with existing semantic colors.
- Long-press drag may reschedule a task. A visible time control in task details remains the required fallback.
- The persistent quick-add dock creates an unscheduled task; `Add and open details` is the path for immediate scheduling.

### 5.3 Weekly

Recommended structure:

1. Sticky week selector with previous, current range, Today, and next.
2. Compact completion summary with count and progress bar.
3. Seven vertical day sections, beginning with today when the active week is current.
4. Each section shows the day/date, completed count, active tasks, and an inline add action.
5. Tapping the day heading opens Daily for that date.

Do not reproduce the desktop seven-column board. Reordering within a day can remain available; moving a task to another day must also be available through an explicit `Move to date` action.

### 5.4 Monthly

- Use a vertically scrolling list grouped by sticky week labels.
- Each day row shows date, up to two active task titles, overflow count, and completed/total count.
- Today uses the brand-filled date marker.
- Tapping a day opens its day agenda; do not depend on double-click to open Daily.
- The day agenda is a full-height layer with `Open Daily`, close/back, task list, and quick add.
- Selecting a task pushes the task-detail layer above the day agenda; Back returns to that day rather than closing the full flow.

### 5.5 Task details

```text
┌────────────────────────────────────┐
│ ‹ Back            TASK DETAILS  × │  Sticky header
├────────────────────────────────────┤
│ □  Finalize API proposal           │
│                                    │
│ Time and duration                  │
│ Repeat                             │
│ Due date                           │
│ Priority / Background              │
│ Notes                              │
│ Subtasks                      1/2  │
│                                    │
├────────────────────────────────────┤
│ Cancel             Done       ••• │  Sticky actions
└────────────────────────────────────┘
```

- Use a full-height sheet or routed layer, not the desktop 420px side drawer.
- Keep buffered editing: Cancel, close, or Escape discards changes; Done commits them.
- Keep completion, time, duration, repeat, detach, due date, category, priority, background, notes, subtasks, promotion, and deletion.
- Put Delete inside a visible overflow action or a dedicated low-emphasis destructive row. It still requires confirmation.
- Opening subtask details pushes a second full-height layer. Back returns to the parent task.
- The sticky footer must remain above the keyboard and bottom safe area.

### 5.6 Quick add

- Resting state: `+ New task` row directly above bottom navigation.
- Active state: inline text field with Add and `Open details` actions.
- Enter adds; Shift+Enter or the details action adds and opens details, matching the current distinction.
- Escape or tapping outside cancels only if no title has been entered.
- On submit, keep the user in the current view and announce success to assistive technology.

### 5.7 Profile and appearance menu

- Show current user identity at the top of the menu, not in the app bar.
- Include theme selection, sign out, home, and secondary links.
- Use a bottom sheet on compact mobile and an anchored popover on wider screens.
- The menu is not a primary planner destination and does not appear in bottom navigation.

## 6. Interaction mapping

| Existing behavior | Mobile path |
| --- | --- |
| Complete task | Tap checkbox; keep row tap reserved for details. |
| Open task details | Tap task body. |
| Add unscheduled task | Persistent quick-add dock. |
| Add and immediately edit | Quick-add details action or Shift+Enter with hardware keyboard. |
| Reorder all-day tasks | Long press or enter reorder mode; visible handle while active. |
| Drag list task into timeline | Optional advanced gesture only; required fallback is setting time in details. |
| Reschedule across days | `Move to date` in details; drag between Weekly sections may be additive. |
| Navigate dates | Previous, Today, next; optional swipe. |
| Change calendar scale | Bottom navigation. |
| Switch Daily panes | Tasks/Timeline segmented control. |
| Open a Monthly day | Single tap opens day agenda. |
| Reach theme/logout | Profile/overflow menu. |

## 7. Responsive states and edge cases

### Empty states

- Daily Tasks: retain all section context and place the quick-add dock in its normal location.
- Timeline: show the hour rail with a quiet `No timed tasks scheduled` message.
- Weekly: show all seven day headings; empty days remain tappable and support adding.
- Monthly: month rows remain navigable even when no tasks exist.

### Loading and errors

- Loading should reserve the full planner shell to avoid layout jumps.
- Sync errors appear below the sticky date block and above content. They must not cover navigation or quick add.
- Long messages wrap, with Dismiss remaining a 44px target.

### Keyboard and browser chrome

- Use dynamic viewport height behavior so browser bars do not crop sticky actions.
- When the keyboard opens, prioritize the active composer or field and its submit action.
- Avoid multiple independently fixed elements above the keyboard; temporarily hide bottom navigation when necessary.

### Offline or delayed sync

- Preserve optimistic task changes.
- Use a small non-blocking sync status near the app bar or an error banner only when intervention is needed.
- Never disable local completion or text entry solely because sync is delayed.

## 8. Accessibility requirements

- Minimum 44px touch targets for primary and icon actions.
- Minimum 16px text for editable inputs to prevent unwanted iOS zoom.
- Visible focus rings and complete keyboard operation remain required on mobile web.
- Do not use color alone for overdue, pending, completed, or selected states.
- Bottom navigation uses semantic navigation and an announced current destination.
- Segmented controls expose tab semantics and preserve focus when content changes.
- Sheets trap focus, restore focus on close, support Escape with a hardware keyboard, and announce their titles.
- Gestures always have visible alternatives.
- Respect `prefers-reduced-motion` and avoid motion longer than the established 200ms overlay transition.

## 9. Visual rules

- Preserve Geist, the near-black/charcoal dark palette, warm-gold brand accent, cool neutral light palette, hairline borders, and restrained shadows.
- Continue using semantic status colors for overdue, pending, completed, and focus states.
- Use 16px mobile gutters and compact 4–16px internal gaps.
- Prefer borders and surface shifts over large shadows. Reserve strong elevation for full-screen or modal layers.
- Do not add gradients, glass effects, decorative imagery, a floating action button, or a new font.

## 11. Acceptance checklist for a later implementation

- [ ] Planner is usable at 320, 375, 390, 430, 768, and 1024px widths.
- [ ] No horizontal page scrolling occurs at supported sizes.
- [ ] Daily defaults to Tasks on first mobile visit.
- [ ] Switching Tasks/Timeline keeps the active date and selected calendar scale.
- [ ] Quick add stays reachable while long task lists scroll.
- [ ] Daily, Weekly, and Monthly remain one tap away from the root planner screen.
- [ ] Every drag-based operation has a visible non-drag alternative.
- [ ] Weekly never renders seven narrow columns below the desktop breakpoint.
- [ ] Monthly day access works with one tap.
- [ ] Task details and day agenda are not wider than the viewport.
- [ ] Detail actions remain visible above browser and keyboard safe areas.
- [ ] Account, theme, and sign-out remain available without crowding the header.
- [ ] Marketing footer does not consume planner viewport space on mobile.
- [ ] Light and dark themes both preserve status contrast.
- [ ] Keyboard, screen reader, reduced-motion, and coarse-pointer paths are covered.
- [ ] Existing desktop behavior is unchanged at 1024px and wider.

## 12. Recommended design sequence

When visual design begins, create and review these states in order:

1. Daily Tasks root screen at 390px.
2. Daily Timeline at the same date.
3. Task details and keyboard-open states.
4. Weekly stacked agenda.
5. Monthly list and day-agenda flow.
6. Empty, loading, error, light-theme, and compact 320px states.

The first review should decide whether the agenda-first structure is correct before investing in the rest of the flow.
