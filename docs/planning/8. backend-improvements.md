# Backend Improvements Roadmap

## Context

A code audit of `backend/` (2026-08-06) surfaced a list of gaps. That list
was then reviewed by a second, external pass (no repo access — working
only from the audit output), which corrected and reprioritized several
items. Each claim from both passes was then checked against the actual
code before finalizing this list. This doc is the reconciled result — not
a transcript, the actual decisions and why.

## How the list changed after verification

- **`created_at` (P0, confirmed):** the audit found `Task.created_at` is a
  `CharField`, not a `DateTimeField` — real, and the top-priority item on
  both passes. The external review's specific claim that lexical string
  ordering is *currently* wrong (due to timezone-offset variance) does
  **not** hold for this app — checked `frontend/src/features/tasks/store.tsx:243,258,558`,
  every `createdAt` value is `new Date().toISOString()`, which is always
  fixed-width UTC (`Z` suffix), so lexical and chronological ordering
  currently agree. The priority stands for the real reasons instead: no
  DB-level date arithmetic, no format validation (a garbage string is a
  valid value), can't be a real migration/index target, and it's a latent
  landmine the moment anything sends a non-UTC-`Z` string.
- **BOLA/ownership "unverified" (corrected):** the external review
  suggested checking task-ownership/IDOR protection before anything else.
  Checked `backend/apps/tasks/tests.py` — this is already covered:
  cross-user requests already 404, and FK ownership (a `repeat_source`/
  `bucket_category` belonging to another user) already 400s, both tested.
  What's actually unverified is narrower: whether `GoogleTokenObtainView`
  checks the Google ID token's `issuer`/`audience`/`expiry` server-side,
  not just that it's validly signed.
- **`subtasks` N+1 (resolved):** the external review flagged needing
  `prefetch_related` on `subtasks` as a maybe. Checked
  `backend/apps/tasks/models.py:55` — `subtasks = models.JSONField(...)`,
  not a relation at all. No `prefetch_related` needed; only
  `select_related("bucket_category", "repeat_source")` for the two real
  FKs the serializer touches per row.
- **Throttling priority (revised down):** the original audit called this
  "the real gap." That overstated it relative to the ownership checks
  that already exist. Still a real, unaddressed gap — just not the
  single biggest one.
- **Pagination (revised down further, confirmed as currently harmful):**
  checked the frontend — it fetches a user's full task list once and does
  all Weekly/Monthly/Bucket filtering client-side
  (`scopeKey(t.scope) === key`-style filters throughout `store.tsx` and
  the view components). Turning on global DRF pagination today would
  change the list-endpoint response shape (`[...]` → `{count, next,
  previous, results}`) and break that immediately — not just
  "premature," actively wrong to do now. Domain-scoped query params
  (`scope_kind`, date range, `updated_after`) are the right next step if
  the full-list approach ever stops scaling; pagination only after that,
  and only on endpoints that actually need it.
- **The item neither pass's original list led with, and should have:**
  reorder/reschedule/nest-as-subtask/promote-subtask-to-task are all
  currently pure client-side operations
  (`frontend/src/features/tasks/lib/nesting.ts`,
  `frontend/src/features/tasks/lib/reorder.ts`) — fractional order math,
  "can't nest a task with its own subtasks," "can't nest/convert a
  repeat-series task" are enforced **only in the browser**. Nesting and
  promotion each fire as two independent, non-atomic API calls from the
  client. Nothing server-side stops a raw API call from nesting a
  repeat-series task or writing a garbage `order` value. This is real and
  currently shippable, not hypothetical — confirmed directly against the
  code that implements those features.

## Priority order

- [ ] **P0 — `Task.created_at`: `CharField` → `DateTimeField`.** Safe
  migration, not a plain `AlterField`: add a nullable `DateTimeField`,
  backfill by parsing the existing strings to UTC, audit any values that
  fail to parse, flip the serializer to read-only for this field (the
  server should own `created_at` for normal creation — a separate
  historical-import path, if one is ever needed for old localStorage
  data, can allow a caller-supplied value explicitly), then drop/rename
  the old column. Matches the existing backfill-migration pattern already
  used in this codebase (bucket categories, task `order`).

- [ ] **P0 — Confirm Google ID token `issuer`/`audience`/`expiry`
  verification server-side.** Not "add ownership tests" (already exist)
  — specifically check `GoogleTokenObtainView`'s verification call
  actually validates these three claims, not just the signature.

- [ ] **P0 — Login serializer: subclass `TokenObtainPairSerializer`.**
  `EmailTokenObtainPairSerializer` currently reimplements Simple JWT's
  logic from scratch rather than subclassing it, which is why its
  failure response drifted from Simple JWT's own convention (400 +
  `non_field_errors` instead of 401 + `detail`/`code`). Fix: subclass and
  call `super().validate()`, layering only the extra user-info response
  fields on top. Add the missing failure-path tests: wrong password,
  non-existent email, inactive user, missing fields, malformed JSON, and
  — the important one — that all of these produce the *same* response
  (don't leak which case it was).

- [ ] **P1 — Fix the N+1 on `TaskListCreateView`.** Add
  `select_related("bucket_category", "repeat_source")`. Prove it, don't
  just apply it: an `assertNumQueries` test asserting the same query
  count at 1 task and at 100 tasks.

- [ ] **P1 — Throttle the auth endpoints specifically**, not a global
  `DEFAULT_THROTTLE_CLASSES`. Scoped `throttle_scope` on login/register/
  Google, separate burst vs. sustained rates, verify the cache backend
  isn't `LocMemCache` if the VM ever runs multiple gunicorn workers
  (per-worker-local cache defeats the point), confirm the real client IP
  is what's throttled (not nginx's `127.0.0.1`) once behind the proxy,
  and test the 429 + `Retry-After` response. Consider that an attacker
  shouldn't be able to lock a real user out by deliberately tripping
  their throttle.

- [ ] **P1 — Unify the error response contract.** Four different shapes
  exist today (`{"detail"}`, `{"error"}`, `{"non_field_errors"}`,
  hand-built field dicts). A custom DRF `EXCEPTION_HANDLER` only covers
  *raised* exceptions — the Google view's hand-built
  `Response({"error": ...}, status=...)` calls bypass it entirely and
  need to be rewritten to raise proper DRF exceptions first. Target shape
  separates a machine-readable `code` from a human `detail`, preserves
  field-level `errors`, and is consistent across 401/403/404/409/429.

- [ ] **P2 — Transactional Task command endpoints.** The main item: turn
  reorder/reschedule/nest-as-subtask/promote-subtask-to-task from
  client-only logic plus generic PATCH/DELETE calls into explicit
  server-side domain operations — `POST /tasks/{id}/reorder`,
  `/reschedule`, `/nest`, `/subtasks/{id}/promote` (or similar). Each
  wrapped in `transaction.atomic()` with `select_for_update()` on the
  affected rows, re-validating ownership and the same business rules the
  client currently enforces alone (no self/descendant nesting, no
  nesting/converting a repeat-series task), with optimistic-concurrency
  handling (a version field, 409 on stale requests) since two tasks are
  mutated per operation. This is genuinely full-stack, not backend-only —
  the frontend's `convertTaskToSubtask`/`promoteSubtaskToTask` store
  actions would call one new endpoint instead of composing two
  independent ones.

- [ ] **P2 — Domain-scoped query params before any pagination.**
  `GET /tasks?scope_kind=day&from=...&to=...`,
  `GET /tasks?scope_kind=bucket&category=...`,
  `GET /tasks?updated_after=<cursor>` for incremental sync. Pagination
  (cursor-based, per-endpoint) only after this, and only where the data
  volume actually justifies it — not a global default.

- [ ] **P2 — Composite indexes matched to real query patterns**, added
  after the query-param work above defines what those patterns actually
  are. `user` as the leading column (every query is user-scoped) —
  something like `Index(fields=["user", "scope_kind", "scope_value",
  "order"])` and `Index(fields=["user", "updated_at", "id"])` are
  plausible candidates, but confirm with `QuerySet.explain()` against
  real queries before adding anything. `scope_kind`/`done` alone are
  low-cardinality, weak standalone index candidates.
