# Backend Improvements Roadmap

_Last reconciled with the codebase: 2026-08-06._

This document contains backend-specific work. The cross-project issue register,
status definitions, and resolution records live in [`docs/refining/`](../refining/README.md).

## Verified completed work

- [x] **Server-owned task timestamps.** `Task.created_at` and
  `Task.completed_at` are real `DateTimeField` values. Migrations 0007-0009
  added shadow columns, backfilled existing strings with an `updated_at`
  fallback for invalid values, and finalized the schema. The serializer treats
  both fields as read-only and derives `completed_at` from the `done`
  transition. Migration and API behavior are covered by tests.
- [x] **Google ID token claim verification.** `GoogleTokenObtainView` calls
  `google.oauth2.id_token.verify_oauth2_token` with the configured audience.
  The installed library verifies signature, issuer, audience, issued-at, and
  expiry claims. Tests verify that the configured audience is passed and that
  verification failures are rejected.
- [x] **Per-user object and relationship ownership.** Task/category querysets
  are scoped to the authenticated user. Cross-owner object requests return 404;
  cross-owner `repeat_source` and `bucket_category` inputs are rejected. These
  paths have API tests.

## Rejected or unproven findings

- [x] **Reject the claimed Task list N+1 as currently unproven.** `subtasks` is
  JSON, not a relation. `bucket_category` and `repeat_source` are represented by
  `PrimaryKeyRelatedField`, whose DRF representation uses PK-only optimization
  and reads the already-selected `<field>_id` value. Do not add
  `select_related()` without a failing `assertNumQueries` test. If the API later
  embeds related objects, re-measure at that point.
- [x] **Reject global pagination as a current improvement.** The frontend
  intentionally loads the complete user task set and filters calendar scopes
  client-side. Global DRF pagination would break the response contract. Add
  domain-scoped queries first and paginate only an endpoint whose measured
  volume requires it.

## Priority work

### P0: server-owned transactional task commands (RF-005)

- [x] Implement task-to-subtask Nest and subtask-to-task Promote as explicit
  command endpoints.
- [x] Wrap those multi-row commands in `transaction.atomic()`, lock affected
  owner/task rows, and revalidate ownership and business rules server-side.
- [x] Add Task version/ETag optimistic concurrency and stable stale-write 409s.
- [x] Make the frontend call one command for Nest/Promote and reconcile failed
  optimistic state before later queued writes.
- [ ] Replace client-composed detach, occurrence-delete, reschedule, and reorder
  behavior with equivalent server commands.

The initial Nest/Promote slice is complete. RF-005 remains In progress only for
the four command families listed in the final unchecked item.

### P0: semantic validation and database integrity (RF-006, RF-007)

- [ ] Validate `scope_kind`/`scope_value` formats and require the correct
  bucket-category relationship for bucket scope.
- [ ] Validate rolled-from field pairing, repeat-source invariants, date/time
  formats, unique weekdays/subtask IDs, and bounded JSON collection sizes.
- [x] Replace case-sensitive category uniqueness plus pre-check with a database-
  enforced Unicode-normalized invariant. Migrations 0010-0012 separate nullable
  AddField, transactional merge/backfill, and full straggler merge/finalize;
  equivalent legacy categories are merged and Task foreign keys repointed.
- [x] Convert concurrent uniqueness conflicts into stable create-or-reuse or
  field-validation responses rather than a 500.
- [x] Align subtask ID/title storage limits with command limits and reject
  over-expanding normalized category keys before production-database writes.

### P1: authentication consistency and abuse controls (RF-009)

- [x] Reuse `TokenObtainPairSerializer` behavior or deliberately preserve its
  401 `detail`/`code` contract while accepting email credentials.
- [x] Cover wrong password, nonexistent email, inactive user, missing fields,
  and malformed JSON. Keep response content consistent and avoid a fast
  nonexistent-user path that creates a password-hash timing distinction.
- [x] Add endpoint-specific login/register/Google throttles with burst and
  sustained limits.
- [x] Use a shared cache when production has multiple gunicorn workers and
  verify Django receives the real client IP through the trusted proxy chain.
- [x] Return and test 429 plus `Retry-After` without enabling account lockout
  abuse.

### P1: one API error contract (RF-014)

- [ ] Define a stable envelope with a machine-readable code, human-readable
  detail, and optional field errors.
- [ ] Raise DRF exceptions instead of returning hand-built Google auth errors so
  the exception handler can normalize them.
- [x] Preserve meaningful Django status codes and `Retry-After` through auth BFF
  handlers. Other API families still need the common envelope above.
- [ ] Document the contract in generated OpenAPI output.

### P1: production verification and observability (RF-011-RF-013)

- [x] Add pull-request CI for backend tests, migration drift, Django checks,
  frontend tests, lint, and production build.
- [ ] Resolve Oracle test-schema permissions or provide a repeatable isolated
  Oracle integration environment.
- [ ] Add liveness/readiness endpoints and a database readiness check.
- [ ] Emit structured application logs to stdout/journald rather than rotating
  one file from multiple gunicorn workers.
- [ ] Document and execute backup restore and deployment rollback exercises.
- [x] Define a maintenance cutover for schema changes: stop old gunicorn writers
  before migrate and coordinate automatic frontend promotion.
- [ ] Execute and record a rollback exercise; documented sequencing alone is
  not rollback proof or zero-downtime deployment.

### P2: measured query evolution

- [ ] Add domain-scoped query parameters such as day/date range, bucket/category,
  and `updated_after` only when the UI can consume them coherently.
- [ ] Capture representative `QuerySet.explain()` and query-count evidence.
- [ ] Add composite indexes that match proven filters, with `user` as the
  leading key where every request is owner-scoped.
- [ ] Add cursor pagination only to endpoints whose volume and access pattern
  justify it.

Plausible future indexes include `(user, scope_kind, scope_value, order)` and
`(user, updated_at, id)`, but they are candidates, not approved changes, until
the corresponding server queries exist and are measured.
